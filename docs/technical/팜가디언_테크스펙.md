# 팜가디언 기술 명세서

> 기술 검토용 초안 · 2026-10-12 제품 범위·요구 동작 갱신. 아키텍처·DDL·쿼리·배치·구현 도구는 기술 총괄과 담당자의 검토·확정이 필요하다. 요구 동작은 현재 [PRD](../shared/팜가디언_PRD.md)·[요구사항 명세서](../shared/팜가디언_요구사항명세서.md)를 따른다.

파랑새 & 뭉즈 · 기존 설계안의 제품 요구사항 갱신 2026-10-12

## 1. 개요

농약 살포 전 4체크(등록·시기·횟수·작용기작)를 공공데이터와 사용자 축적 이력으로 판정하는 웹 서비스의 기술 명세다.

기능 정의는 `../shared/팜가디언_요구사항명세서.md`에 있다. 이 문서는 그것을 어떻게 구현할지를 다룬다.

**설계 원칙 세 가지**

1. 판정은 규칙 기반이다. 판정 경로에 추론 모델을 넣지 않는다.
2. 판정 처리 중 외부 공공 API·OCR의 실시간 성공에 의존하지 않는다. 준비된 원자료·규칙·이력을 사용한다. 적재·갱신 구현은 기술 담당자가 정한다.
3. 근거가 없으면 판정하지 않는다. `UNKNOWN`을 반환하고 부족한 근거를 명시한다.

### 2.1 구성

```

  React 모바일 웹

        |
        | REST (JSON)
        v
[ 애플리케이션 ]
  API 서버
    ├─ 판정 엔진        순수 함수 모듈. DB·네트워크 비의존
    ├─ 조회 서비스      약제·병해충·기준·이력 read
    ├─ 이력 기록 서비스  write
    └─ 명칭 정규화      사전 기반 매칭
        |

    ├─ 적재 데이터   safe_use_std, pesticide, moa, registration, pest, pest_candidate
```

### 2.2 외부 API를 판정 경로에서 분리한 이유

| 얻는 것 | 설명 |
|---|---|
| 가용성 | 외부 API 장애·지연이 판정을 막지 않는다. 시연 중 외부 공공 API 문제가 발생해도 준비된 자료로 판정한다 |
| 재현성 | 기준일이 고정되므로 같은 입력에 같은 판정이 나온다. 사후에 판정 근거를 재구성할 수 있다 |
| 리스크 격리 | 안전사용기준 자연어 파싱 실패를 배치 단계에서 걸러낸다. 실패한 기준은 해당 체크의 확인 필요 사유와 원문으로 표시한다 |

경계 조회·기본 날씨·P1 OCR은 판정 계산과 분리한다. 호출 위치·캐시·갱신 시점은 기술 담당자가 정한다.

| API | 시점 | 사유 |
|---|---|---|
| 팜맵 | 밭 등록·경계 조회 | 조회 실패를 안내하고 재시도 가능 |
| 기상청 | 판정 화면의 기본 날씨(P0) | 예보 발표 시각·출처·실패 상태 표시, 판정은 유지 |
| 포장지 OCR | 이력 입력(P1) | 제품 후보 연결, 실제 구역·날짜는 사용자 확인 |

## 3. 기술 스택

| 계층 | 선택 | 사유 |
|---|---|---|
| 클라이언트 | React, 모바일 웹 | 스토어 심사 없이 배포한다. 현장에서 링크로 즉시 열린다 |
| API 서버 | FastAPI | 프레임워크 선택으로 판정 규칙을 변경하지 않는다 |
| 판정 엔진 | 순수 함수 모듈 | 단위 테스트로 전 분기를 검증한다 |
| DB | **Supabase** (Postgres + PostGIS) · RLS 적용 | 2026-10-15 확정. 마이그레이션·시드·RLS 정책은 [DB_시드_전달서.md](DB_시드_전달서.md) 3절 |
| 로그인 | **Supabase Auth 카카오 공급자** | 2026-10-15 확정. `auth.users` ← `app_user` 프로필 테이블 |
| 배치 | 스케줄러 도입 여부 검토 | 실제 자료 갱신 필요·주기 확인 후 결정 |
| 지도 렌더링 | SVG (팜맵 좌표 정규화) | 지도 타일 의존을 제거한다. 4장 참조 |

### 3.1 지도 렌더링 방식

팜맵 API가 반환하는 것은 필지 폴리곤 좌표다. 지도 타일은 포함되지 않는다.

**구현 방식**
```
팜맵 폴리곤 좌표
  → bounding box 계산
  → SVG viewBox에 맞춰 정규화
  → <polygon points="..."> 렌더링
  → 구역 분할선, 상태 표시, 작용기작 편중 오버레이
```

좌표는 실제 값이므로 필지 모양은 실제와 같다. 배경 항공영상 없이 렌더링한다.

**이유**
- 항공영상 배경 위에서는 상태 색상과 라벨의 가독성이 떨어진다
- 지도 타일 API 의존과 인증키가 하나 줄어든다
- 준비한 경계로 외부 지도 API 장애의 영향을 줄일 수 있다. 오프라인 저장을 요구하는 것은 아니다

항공영상 배경은 이전 설계 제안이며 현재 P1 제품 기능으로 확정하지 않았다. FR-101·102의 실제 경계 조회·균등 면적 분할·직접 선 그리기·경계 수정 요구를 만족하는 렌더링과 공간 연산 방법을 기술 담당자가 정한다.

## 4. 데이터 모델

**스키마 정본은 [DB_시드_전달서.md](DB_시드_전달서.md) 3-1절이다.** 여기에 DDL을 복제하지 않는다. 두 벌이 있으면 반드시 어긋난다.

```
환경    Supabase (Postgres + PostGIS + Auth 카카오) · 전 테이블 RLS
테이블  16개 (auth.users 제외)
적재    supabase/migrations/20261015000000_init.sql + supabase/seed.sql
명령    로컬 supabase db reset / 원격 supabase db push
```

| 묶음 | 테이블 |
|---|---|
| 사용자 | `app_user` (`auth.users` 프로필) |
| 참조 — 병해충 | `crop` `pest` `pest_alias` `pest_season` `pest_photo` `virus_vector` |
| 참조 — 약 | `pesticide_use` `safe_use_std` `ingredient` `use_ingredient` `moa` `rotation_rule` |
| 사용자 데이터 | `field` `zone` `spray_log` |

`registration`(등록취소)·`resistance_ref`(논문 실측값)는 자료가 없어 V002로 미뤘다.

### 4.1 설계 결정 — 바꾸면 안 되는 것

| 결정 | 이유 |
|---|---|
| **작용기작은 `ingredient.moa_id`** | 계열은 약이 아니라 성분의 속성이다. 혼합제(더블킥 = 아바멕틴 + 스피네토람)는 `use_ingredient`에 두 줄. 약에 직접 붙이면 혼합제를 표현할 수 없다 |
| **잔여 횟수·계열 카운트를 컬럼으로 저장하지 않는다** | `spray_log`에만 기록하고 조회 시 계산. 저장하면 취소·수정에서 어긋난다 |
| **취소는 `cancelled_at` 소프트 삭제** | 물리 삭제하면 「언제 뭘 취소했나」가 사라진다 |
| **`pesticide_use.use_time` / `use_count`는 PSIS 원문 그대로** | 화면에 근거로 띄운다. 파싱 결과만 남기면 되돌릴 수 없다 |
| **`safe_use_std.parse_status`를 행 단위로 기록** | 파싱 실패를 약 전체가 아니라 그 행만 격리한다. 실패한 약도 목록에 남기고 해당 체크만 ⚪ |
| **`moa`에 `kr_code`와 `intl_code` 둘 다** | 국내 표기(가1, 5)와 국제 코드(FRAC 4, IRAC 5)를 함께 보여준다 |
| **`pest_alias`를 따로 둔다** | PSIS「역병」 / NCPMS「감자역병」 / 발생정보「감자역병(고랭지 씨감자)」 — 이름이 소스마다 다르다. 매칭에 실패하면 약 목록이 0건이 된다 |
| **`spray_log.verdict_snapshot` (JSONB)** | 저장 시점의 판정을 남긴다. 원자료가 갱신돼도 「그때 무엇을 보고 뿌렸나」가 남는다 |

### 4.2 파생값은 조회 시 계산한다

- **③ 잔여 횟수** — 성분 기준. 같은 성분 + 같은 처리법(`route`) 약들의 `max_count` 중 최솟값에서 사용 횟수를 뺀다. SQL은 [전달서 4절](DB_시드_전달서.md)
- **④ 계열 반복** — `spray_log → pesticide_use → use_ingredient → ingredient → moa`
- **계통 사용 비중** — 이번 작기 이력의 계열별 비율. 약효·저항성 수준이 아니다

### 4.3 사용 방법 정규화 (`route`)

`pesticide_use.method`는 PSIS 원문이다(고유 65종). 괄호를 떼고 끝말을 뽑으면 **12종**이 된다. 수집 자료 3,870줄 전부 파싱된다.

```python
def to_route(method: str | None) -> str | None:
    if not method:
        return None
    m = re.search(r'(\S+처리|\S*혼화)$', re.sub(r'\(.*?\)', '', method).strip())
    return m.group(1) if m else None        # 새 끝말·NULL이면 None → 한도 계산 안 함, ⚪
```

`.group(1)`을 바로 부르면 일치 실패에 `AttributeError`, `method`가 NULL이면 `TypeError`가 난다. `method`는 DDL에서 NULL을 허용한다.

```
경엽처리 3260 · 토양처리 366 · 관주처리 134 · 침지처리 28 · 토양혼화 26
분무처리 18 · 훈연처리 18 · 파구처리 6 · 분의처리 5 · 육묘상처리 4 · 상토처리 3 · 점적처리 2
```

③ 한도를 처리법별로 나누는 데 쓴다. 육묘상 관주(한도 1)가 경엽 살포(한도 3)를 끌어내리지 않게 한다. 새 끝말이 나와 `route`가 NULL이면 한도를 계산하지 않고 ⚪로 둔다.

### 5.2 PSIS

```
요청 URL   http://psis.rda.go.kr/openApi/service.do        (농약 등록정보)
           http://psis.rda.go.kr/openApi/cnclAgchm.do      (등록취소)

파라미터   apiKey        발급받은 인증키

```

**주의**
- `displayCount` 최대가 50이다. 전량 수집 시 호출 횟수가 많다. 초기 적재는 웹 화면의 엑셀 다운로드를 병행 검토한다.
- 안전사용기준은 자연어 문장으로 제공된다. 5.5 참조.

**검색 조건**: 작물명, 병해충명, 용도, 품목명, 상표명, 회사명

### 5.3 병해충 도감·발생시기·매개충 자료

수집한 도감·사진·발생시기·등록약·바이러스 매개충 자료를 연결해 FR-201~205를 구현한다. 발생시기는 출처·기준 시점과 함께 참고 표시하고 시기가 지났다고 후보를 제외하지 않는다.

이름 검색은 도감과 수집한 등록약 자료의 병해충 이름을 포함한다. 사진·설명·연결 자료가 없으면 해당 정보 없음으로 구분한다. 확인된 바이러스·매개충 연결에서 사용자가 매개충을 직접 선택한 후 그 작물·매개충의 등록 약제 판정으로 연결한다.

실시간 예측 순위·현재 경보를 필수 기능으로 추가하지 않는다. 원자료 갱신 방식·외부 연동 필요 여부는 기술 담당자가 정한다.

### 5.4 팜맵 / 기상청

**팜맵 (EPIS)**
- 농경지 전자지도. 항공영상 판독으로 구축된 실제 경작 경계
- 지적도와 다르다. 소유 경계가 아닌 경작 경계다
- 좌표계 확인 필요. 국내 공간정보는 통상 EPSG:5179
- 매년 갱신. `field.farmmap_version`에 기록
- 강원 지역 shp을 사전 다운로드해 오프라인 백업으로 확보한다

**기상청 단기예보**
- P0 기본 날씨: 선택 구역 위치의 시간대별 강수 예보·발표 시각·출처를 표시한다.
- 좌표 변환·예보 상품·항목 코드·갱신 주기·실패 응답은 실제 API 문서와 응답을 기준으로 기술 담당자가 확인한다.
- 실패 상태를 화면에 안내하며 판정·기록·조회·취소는 계속 사용한다. 예보로 별도의 살포 가능·불가를 판정하지 않는다.

### 5.5 안전사용기준 파싱

프로젝트 최대 리스크 구간이다.

**입력 형태 (예상)**
```
"수확 21일 전까지, 3회 이내 사용"
"본엽 4매기 이후부터 수확 21일 전까지, 3회 이내"
"정식 전 토양혼화, 1회"
"수확 7일 전까지, 3회 이내 (단, 저온기 재배 시 10일 전까지)"
```

**목표 출력**
```json
{ "phi_days": 21, "max_count": 3, "stage_from": null }
{ "phi_days": 21, "max_count": 3, "stage_from": "본엽 4매기" }
{ "phi_days": null, "max_count": 1, "stage_from": "정식 전 토양혼화" }
```

**진행 순서**

1. 이미 수집한 원자료를 우선 대조해 필드·문장 형태를 확인한다. 추가 API 표본이 필요한 경우 담당자가 범위와 수량을 정한다.
2. 문장 패턴을 분류한다.
3. 패턴이 20~30개로 수렴하면 정규식으로 처리한다.
4. 패턴이 불규칙하면 토큰 분류(NER) 모델을 검토한다. 라벨은 표본 검수 결과를 사용한다.
5. 어느 방식이든 실패 행은 `parse_status = 'failed'`로 저장하고 원문을 유지한다.

**검토 사항**: 파싱 방법·표본 수·성능 기준은 실제 자료를 보고 기술 담당자가 정한다. 위 방식은 구현 제안이며 숫자를 확정 품질 목표로 사용하지 않는다. 추론 모델을 판정 요청 처리 중 호출하지 않는 원칙은 유지한다.

**주의**: 파싱 실패 자체는 허용된다. 실패한 행이 `GREEN` 판정에 쓰이는 것이 결함이다.

## 6. 배치 설계

### 6.1 적재·갱신 검토

대상 작물 3종의 수집 엑셀 7개가 준비돼 있다. 신규 데이터 수집을 P0 선행 기능으로 두지 않는다. 구현 중 자료 연결·파싱·등록·사용기준·반복규칙 검증과 필요한 데이터 갱신을 확인한다.

주기적 API 적재가 필요한지, 갱신 대상·주기·스케줄러·실패 처리는 기술 담당자가 정한다. 이전의 야간 시각과 예측·예찰 배치 목록을 확정 작업으로 사용하지 않는다.

### 6.2 유지할 요구 동작

- 외부 공공 API·OCR 호출의 실시간 성공에 판정이 의존하지 않는다.
- 확보한 원자료·기준일을 추적하고, 파싱 실패는 원문과 체크별 확인 필요 사유로 구분한다.
- 같은 입력·원자료·규칙·기준일이면 같은 결과를 제공한다.
- 데이터 갱신·실패 처리가 이전 자료를 임의로 통과 근거로 만들지 않도록 검증한다.

## 7. 판정 엔진

### 7.1 계약

```
judge(zone, candidate, today, history, rules) -> Verdict
```

**입력**

```
zone      { zone_id, crop_id, planted_at }          planted_at이 null이면 ③④ UNKNOWN
candidate {
  use_id, pest_id, route,                            route는 정규화된 처리법 (4.3절). NULL 가능
  product, brand, company, usage, dilution,          출력 Verdict.pesticide를 만들려면 필요하다
  phi_days, max_count, parse_status,
  use_time, use_count,                               PSIS 원문. Check.evidence.raw_text가 된다
  base_date,                                         자료 기준일. Check.evidence.base_date가 된다
  registered,                                        ① 판정용. 등록 행 존재 여부
  ingredients: [ { ingredient_id, name,
                   moa: { kr_code, intl_code, is_multi_site } | null } ]
}
today     'YYYY-MM-DD'                               인자로 받는다. 내부에서 조회하지 않는다
history   [ { use_id, route, sprayed_at,
              ingredients: [ { ingredient_id, max_count, parse_status,
                               moa: {...} | null } ] } ]
rules     [ { moa_scope, window_unit, window_size, max_consecutive, source, description } ]
```

**출력** — `Verdict` (전체 모양은 [api-spec 2-1절](api-spec.md))

```
{ state, checks: [Check, Check2, Check3, Check4], base_date }
```

`candidate.ingredients`가 배열인 것이 핵심이다. 혼합제는 성분마다 ③④를 따로 계산하고 가장 나쁜 쪽이 전체 상태가 된다.

**`use_time`·`use_count`·`base_date`를 입력에 넣는 이유:** 제약 4가 모든 `Check`에 `evidence`(원문·출처·기준일)를 요구한다. 순수 함수는 DB를 못 읽으므로 원문이 인자로 들어와야 한다. `product`·`brand`도 같은 이유다 — 출력 `Verdict.pesticide`를 만들어야 한다.

**구현 제약 다섯**

1. 시그니처에 **DB 커넥션·HTTP 클라이언트·로거를 받지 않는다**
2. 내부에서 **현재 시각을 조회하지 않는다.** `today`를 인자로 받는다
3. 프레임워크 애노테이션을 붙이지 않는다. 별도 모듈로 분리한다
4. 모든 `Check`에 `evidence`(원문·출처·기준일)를 채운다. 없는 근거를 만들지 않는다
5. **LLM·머신러닝 모델을 호출하지 않는다**

제약 1·2·3이 단위 테스트를 가능하게 하고, 2가 재현성을 보장한다. 같은 입력·같은 기준일이면 언제 돌려도 같은 판정이 나와야 한다.

### 7.2 판정 동작

판정 계산은 FR-302, 일관성은 FR-303, 목록 정렬·표시는 FR-304를 따른다. FR-303은 별도의 사용자 조작이 아닌 공통 판정 기준이다.

| 체크 | 근거가 충분한 경우 | 확인 필요 조건 |
|---|---|---|
| ① 등록 | 확인된 유효 등록이면 가능, 확인된 미등록·등록취소 등은 불가 | 병해충 미선택·필요한 등록 근거 부족 |
| ② 시기 | 확인된 수확 전 일수와 필요한 조건으로 수확 가능 날짜 계산 | 기준값·원문 해석·추가 조건 정보 부족. 정식일 없음 자체를 일괄 실패 조건으로 두지 않음 |
| ③ 횟수 | 기존 사용 + 이번 1회가 최대 횟수 이내면 가능, 초과하면 불가 | 이력 0건·재배 기간·사용한도·필요한 이력 부족 |
| ④ 작용기작 | 이번 1회를 포함한 확인된 반복규칙 미초과면 가능, 초과하면 주의 | 이력 0건·계통·규칙·필요 정보 부족 |

**③ 합산 단위는 성분 기준으로 확정됐다** (2026-10-15). 한도는 같은 성분 + 같은 처리법(`route`) 약들의 `max_count` 중 최솟값이고, 사용 횟수는 처리법과 무관하게 전부 센다. 혼합제는 성분마다 따로 계산해 하나라도 한도에 닿으면 불가다.

`parse_status`를 보지 않고 ②③을 통과시키지 않는다 — `ok`는 계산, `stage`는 ②만 ⚪, `no_std`·`failed`는 ②③ 모두 ⚪다. **빈칸은 「제한 없음」이 아니다.**

② 추가 사용조건의 위반 처리, ④ 규칙 충돌·미분류·충분한 이력의 범위는 검증 후 확정한다. 사용기준 행이 없다는 이유만으로 불가를 만들지 않는다.

최종 상태 우선순위는 RED > NA > UNKNOWN > AMBER > GREEN. `NA`는 심을 때 쓰는 약(`parse_status=stage`)이라 ② 항목 자체가 없는 경우이며, 값을 못 읽은 `UNKNOWN`과 구분한다. 목록 정렬 순서는 GREEN → AMBER → NA → UNKNOWN → RED이며 불가 약제도 사유와 함께 표시한다.

불가·주의이면 현재 약제와 다른 작용기작의 등록 약제를 대안 후보로 판정해 GREEN인 것만 제시한다. 대안 0개일 때만 농업기술센터 문의를 안내한다. 다작용점 우선 정렬은 현재 적용하지 않는다.

### 7.3 검증 사례

| 사례 | 확인할 결과 |
|---|---|
| 검증된 기준·이력으로 한도 이내 | 체크별 가능·근거·전후 잔여 값 |
| 마지막 허용 1회 | 사용 후 잔여 0이어도 이번 사용은 한도 이내 |
| 이번 사용 포함 한도 초과 | ③ 불가 |
| 확인된 반복규칙 초과 | ④ 주의·규칙 사유 |
| 이력 0건 | ③④ 확인 필요 |
| 병해충 미선택 | ① 확인 필요·다른 체크는 각자의 근거로 판단 |
| 원문 해석 실패·자료 없음 | 관련 체크 확인 필요·원문 또는 누락 사유 |
| 정식일 없음 | 적용 가능한 사용기준이면 ② 계산·③④는 필요한 기간·규칙 확인 |
| 동일 조건 재판정 | 동일 결과·실제 기록 증가 없음 |
| 외부 API·OCR 장애 | 준비된 자료의 판정 유지 |
| **혼합제** (더블킥 = 아바멕틴 + 스피네토람) | 성분마다 ③④ 따로. 하나라도 한도에 닿으면 ③ 불가. 화면에는 가장 적게 남은 성분 |
| **같은 성분 다른 상표** (엑설트 2회 → 델리게이트) | 한도 = min(두 약의 max_count). 순서를 바꿔도 같은 결과 |
| **처리법이 다른 같은 성분** (격파 육묘상 1회 → 엑설트 경엽) | 경엽 한도는 육묘상 약의 1에 끌려가지 않는다. 사용 횟수에는 포함 |
| **`parse_status='failed'`** | 숫자 칸에 값이 있어도 쓰지 않는다. ②③ 확인 필요 + 원문 |

## 12. 일정과 분담

기존 날짜별 구현 일정은 현재 실행 일정으로 사용하지 않는다. 문서 검토 결과를 바탕으로 WBS·백로그에서 담당·기간·선행 작업을 확정한다. P0 완료 후 P1을 진행하고 P2는 별도 고도화 착수 합의 후 진행한다.

현재 데이터 수집 자료는 준비돼 있다. 적재·연결·규칙 검증은 해당 기능의 구현 작업으로 계획한다.
